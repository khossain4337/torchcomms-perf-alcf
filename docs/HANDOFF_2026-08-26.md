## ▶ SUMMARY — read this, then skip to whatever you need

The 48-rank XCCL bootstrap hang is **fixed**, and the first real benchmark data
from this work now exists.

**The bug:** `PBS_NODEFILE` on Sunspot holds *already-qualified* names
(`x1921c1s0b0n0-hsn0.hsn.cm.sunspot.alcf.anl.gov`). Appending an HSN suffix
doubled the domain, `MASTER_ADDR` stopped resolving, and every rank reached the
XCCL UniqueID exchange while none completed it — a silent hang with no error.
Fix: strip to the bare nodename, then append `.hostmgmt.cm.sunspot.alcf.anl.gov`,
and `getent hosts` it in the job script so a bad address costs a second instead
of a walltime. Commit `a8dad00` in `run_minimal.sh`.

**The data:** two clean 48-rank runs (4 nodes × 12 rpn), `all_reduce` float32
sum, sync dispatch, 1 KiB–64 MiB, warmup 20 / iters 100. Run
`minimal_2026-08-26-020554` covers **all three adapters** in one job.

| | 1 KiB | 1 MiB | 64 MiB |
|---|---|---|---|
| torchcomms | 108.8 µs | 199.2 µs | 2413.8 µs / **54.45 GB/s** busbw |
| c10d | 111.2 µs | 200.5 µs | 2466.3 µs / 53.29 GB/s |
| c10d_torchcomms | 129.6 µs | 209.7 µs | 2427.4 µs / 54.14 GB/s |

**The headline result: the adapters differ, and torchcomms is fastest.**
That was the open question since 2026-08-20 and it is now answered.
torchcomms beats both others at **17/17 sizes** (sign test p ≈ 7.6e-6).
The gap is a fixed per-call overhead, not a bandwidth difference: **+6.3%
(c10d) and +11.5% (c10d_torchcomms) below 256 KiB, collapsing to ~1% above
4 MiB**, where wire time dominates. Large-message busbw is within 2% across all
three — as it must be, since all three drive the same XCCL/oneCCL stack.

**Traffic went over CXI/Slingshot, not TCP.** 27.8 GB/s algbw at 64 MiB is 222×
the entire 0.125 GB/s management link. `MASTER_ADDR` carries only the bootstrap
handshake; transport is oneCCL's (`CCL_ATL_TRANSPORT=mpi` → MPICH → libfabric
`cxi`).

**Health check:** busbw still climbing at 64 MiB (41 → 48 → 54 GB/s over the top
octave) — the curve has not saturated, so 64 MiB is not yet the asymptote.
Run-to-run spread on repeated points is ≤0.4% at ≥8 MiB but ±3–6% below 1 MiB.

**Next:** scale nodes (4 → 8 → 16 → 32), then add collectives. Blocker for the
ladder: `sites/common.sh:114` still yields the `-hsn0` rendezvous address and
will reproduce the hang. One line, not yet changed — needs a go-ahead.

routed through torchcomms — being the slowest of the three is consistent with it
paying both layers' overheads. Worth a profile before treating that as
established.

## Did the data cross the fabric? Yes.

Three independent arguments:

1. **Arithmetic.** Management network is 1000 Mb/s = **0.125 GB/s**. Measured
   64 MiB algbw is **27.8 GB/s — 222×** that. Even the 1 MiB point (5.4 GB/s) is
   43× over. Physically impossible over `hostmgmt`.
2. **Architecture.** `MASTER_ADDR` carries the UniqueID handshake only, once, at
   init. Transport is selected independently by oneCCL:
   `CCL_ATL_TRANSPORT=mpi` → MPICH → libfabric → `cxi` (first provider listed).
   A management-net rendezvous is therefore normal, not a compromise.
3. **Shape.** busbw rising 10.3 → 32.4 → 54.5 GB/s across 1/8/64 MiB is a ring
   filling up. TCP over 1 GbE would be flat near 0.1 GB/s.

**Rough efficiency, stated as a range because the NIC count is unconfirmed.**
Per-node inter-node egress at 64 MiB is 100.7 MB (hierarchical: intra-node
reduce, then a 4-node ring) to 131.4 MB (flat 48-rank ring), i.e. **42–54 GB/s
per node, 334–436 Gb/s**. Against 2 NICs × 200 Gb/s that is 83–109% of line
rate; against 8 NICs it is 21–27%. **This checks the order of magnitude only.**
Sunspot compute nodes are 8× CXI (the `ls /sys/class/net` showing hsn0/hsn1 was
run on `aurora-uan-0011`, a login node — do not use it for compute-node NIC
count), and both figures are lower bounds since the 2.41 ms window also contains
intra-node reduce/bcast. Do not quote an efficiency percentage from this without
confirming NIC count and the actual oneCCL algorithm.

**To settle it directly on the next run**, add:

```bash
-genv CCL_LOG_LEVEL info -genv FI_LOG_LEVEL warn
```

oneCCL then names the provider and the algorithm it selected. Cheap; do it once.

## The fix, in the form worth copying

```bash
_master_node=$(head -n 1 $PBS_NODEFILE)
_master_node=${_master_node%%.*}      # strip the domain PBS already added
_master_node=${_master_node%-hsn0}    # and the fabric-interface tag
export MASTER_ADDR=${_master_node}.hostmgmt.cm.sunspot.alcf.anl.gov
export MASTER_PORT=29500

if ! getent hosts "${MASTER_ADDR}" >/dev/null 2>&1; then
    echo "FATAL: MASTER_ADDR=${MASTER_ADDR} does not resolve" >&2
    exit 1
fi
```

Strip-then-append is correct whether or not the nodefile is qualified. The
`getent` guard is the important half: it converts a whole-walltime hang into a
one-second failure at submit.

Why `.hostmgmt` and not `-hsn0`: the only multi-node torchcomms bootstrap that
had ever completed here (`logs/N2_R12_2026-08-05-180711`, 2 nodes × 12) used it.
On Sunspot both forms resolve to exactly one address, so the usual
"avoid multi-homed names" rule does not choose between them — that reasoning is
what put the wrong suffix in the script in the first place.

## Next actions, in order

1. **Scale the node count: 4 → 8 → 16 → 32.** Same collective, same sizes, so
   the axis is clean. `run_minimal.sh` derives `NRANKS` from `PBS_NODEFILE`, so
   only the `select=` needs to change. This is the user's primary goal.

2. **Add `-genv CCL_LOG_LEVEL info`** to one run and record which algorithm and
   provider oneCCL picks. Turns the efficiency estimate above into a fact.

3. **Broaden collectives** — `all_gather`, `reduce_scatter`, `broadcast`,
   `all_to_all`. Note `send_recv` needs an even rank count and skips otherwise.

4. **Fix the ladder's rendezvous address.** `tcperf_reachable`
   (`sites/common.sh:114`) passes qualified names through unchanged — so no
   doubling — but hands back the `-hsn0` address, which is the address that
   hangs. `sites/sunspot.sh:9` sets `TCPERF_HSN_SUFFIX`. **Deliberately not
   changed**: `bin/tc-perf-env` is off-limits and `sites/` is shared. Needs a
   go-ahead. Until then the ladder cannot run.

5. **Repeat ×3 for error bars** at whatever node count becomes the headline.
   Single-run small-message numbers are ±3–6%.

6. **Optional:** run under `TCPERF_CCL_SYNC=0` as well as the default. The gap
   is itself a result.

The 08-20 list still holds: `set -u` + Lmod, `PYTHONPATH` shadowing,
`MASTER_ADDR` computed once outside `mpiexec`, `python` absent before the module
loads, tegu and flare mutually invisible.

**New:** never append a suffix to a `PBS_NODEFILE` entry without stripping
